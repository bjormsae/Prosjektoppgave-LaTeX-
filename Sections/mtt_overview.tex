\section{Multi-Target Tracking: An overview}
\label{sec:mtt-overview}

% ---- Opening + reading guide --------------------------------------
Multi-target tracking (MTT) is the problem of estimating the number of targets and their states over time from noisy, incomplete and ambiguous sensor data. This section is organized around one idea: \emph{a tracker is assembled from interchangeable building blocks}, and the named methods in the literature result from particular block choices. Section~\ref{sec:formulation} states the problem and why it is hard. Section~\ref{sec:anatomy} introduces the blocks and the options for each. Section~\ref{sec:complexity} shows that many of these options exist to manage combinatorial complexity, and Section~\ref{sec:multisensor} covers the second concern that cuts across the blocks: combining data from several sensors. Section~\ref{sec:map} uses the blocks to draw a map of the field, and Section~\ref{sec:families} describes each family in detail. Section~\ref{sec:outside} covers methods that do not fit completely into the standard pipeline. Section~\ref{sec:selection} compares the families and turns the comparison into design choices for this project. Colors identify families consistently throughout.

\subsection{Problem formulation}
\label{sec:formulation}
The following problem statement is based on the commonly used Detection Based Tracking (DBT) paradigm. This formulation assumes that a detector supplies detections of objects in a sensors field of view (FOV)\footnote{The addition of clutter (false alarms) and probability of detection ($\PD$) less than one arises naturally from classical detection theory, where detecting noisy objects leads to an inevitable tradeoff between lots of clutter and a high $\PD$ \cite{detection_theory}.}.
\medskip

Let $X_k=\{\mathbf{x}_k^{1},\dots,\mathbf{x}_k^{N_k}\}$ be the set of target states at time $k$, with $N_k$ unknown and time-varying. Each target survives with probability $\PS$ and evolves as $\mathbf{x}_{k+1}=f(\mathbf{x}_k)+\mathbf{w}_k$. Each target is detected with probability $\PD$, producing $\mathbf{z}_k=h(\mathbf{x}_k)+\mathbf{v}_k$. New targets appear according to a birth model. 
\medskip

$Z_k = \{\mathbf{z}_k^{1},\dots,\mathbf{z}_k^{M_k} \bigcup \mathbf{C}_k\}$ is the set of measurements received.
The set $Z_k$ contains both measurements generated by targets $\mathbf{z}_k^i$ and clutter $\mathbf{C}_k$, and the origin of each measurement is unknown. Clutter is generated according to a clutter model.
\medskip

MTT aims to estimate the optimal sequential states $X_{1:t}$, based on the measurements $Z_{1:t}$. This can be formulated as the following MAP (Maximum a posteriori) estimation problem as presented in \cite{mtt_litterary_review}.

\begin{equation*}
  \widehat{\mathbf{X}}_{1:t} = \operatorname*{arg\,max}_{\mathbf{X}_{1:t}} P\left(\mathbf{X}_{1:t} \mid \mathbf{Z}_{1:t}\right).
\end{equation*}

\textcite[Sec.~2]{mtt_litterary_review} then writes that ``different MOT algorithms from previous works can now be thought as designing different approaches to solving the above MAP problem, either from a probabilistic inference perspective or a deterministic optimization perspective.''
\medskip

Tracking can also be split into online and batch methods. Online trackers process measurements recursively and will be the main focus of this overview. Batch methods process multiple sets of measurements and estimate the entire tracks jointly. \TODO{Maybe add that a lot of probabilistic inference is recursive and a lot of batch methods are optimization based. \subsubsection{Why is MTT difficult?}
There are a handful of features which makes the MTT problem hard to solve. It is worth stating these explicitly, as the building blocks of an MTT algorithm are made to address different problems. \autoref{tab:challenges} lists the main difficulties and which parts of the tracker that addresses this difficulty.

\subsection{Anatomy of a tracker: the building blocks}
\label{sec:anatomy}

The following section will present the main building blocks of a multi target tracker. Note that the breakdown into blocks is most useful for describing online recursive tracking methods, which will become clear when characterizing named methods in literature based on block choices. Depending on the method, these blocks may be more or less intertwined or implicitly handled. This section will nonetheless express these blocks as easily interchangeable, since it can be a very useful abstraction. Thinking of a tracker in terms of building blocks is also useful since the blocks themselves tie back to the inherent difficulties of the tracking problem as presented in \autoref{tab:challenges}. All feasible algorithms aiming to solve the MTT problem need to address these difficulties in some way.

\autoref{fig:pipeline} shows the building blocks and information flow of a recursive tracker. State predictions and detections are gated before doing inference. Inference is often broken down into data association, state update and hypothesis management. The leftover tracks are then predicted again until new detections arrive. Some factors like the sensor model have been omitted from the figure since it is used implicitly in multiple places in the pipeline. \autoref{fig:pipeline} should therefore be seen in combination with \autoref{tab:designspace}, where each block has been decomposed into the actual choices that can be made for each block. \autoref{tab:designspace} then includes examples of both classical and learned options for each choice.
\medskip

To illustrate the modularity of tracking algorithms we will present an example in the form of StrongSORT \cite{strongSORT}, which takes DeepSORT~\cite{deepSORT} and upgrades it one block at a time. In the terms of \autoref{tab:designspace}, DeepSORT combines a learned front-end (CNN detector) and a learned re-ID association cost with an otherwise classical back-end: a constant-velocity Kalman filter, Mahalanobis gating, hard association solved by Hungarian matching in a cascade, and a hit/miss counter for track confirmation and deletion. StrongSORT then replaces, one at a time, the re-ID network with a stronger one and the per-track feature bank with an exponential moving average of embeddings (association cost); the constant measurement noise with one scaled by detector confidence, $\tilde{R}_k = (1-c_k)R_k$ (sensor model: a learned quantity inside a classical filter); appearance-only matching with a weighted sum of appearance and kinematic cost (association cost); adds camera-motion compensation to the prediction (motion model); and replaces the matching cascade with a single global assignment (association solver). The mixed upgrades yielded a better performance when compared to DeepSORT, indicating that freely picking blocks not only works, but can increase performance. However, the paper also notes that the matching cascade increased performance in DeepSORT, but decreased it in StrongSORT, motivating the change. This illustrates that although one can pick blocks freely, the best option for one block may depend on the choices made for the others.

\subsubsection{Front-end: detections or raw data}
Points to make:
\begin{itemize}
    \item The tracking algorithm we design is only as good as the detectors we use.
    \item Many modern image detectors can provide feature information alongside the detections. See re-ID.
    \item Do the detectors provide multiple detections for the same object? Important to know if we must use extended object tracking or not
    \item The classic split between track by detect and track before detect.
\end{itemize}

\subsubsection{Sensor model}
Points to make:
\begin{itemize}
    \item Components: state to measurement function, clutter distribution, $P_D$.
    \item Changing $P_D$ can improve performance when objects are occluded. 
    \item Knowing where clutter is likely is very powerful for gating and data association.
\end{itemize}

\subsubsection{Motion model and filter}
Points to make:
\begin{itemize}
    \item Classically built upon the Kalman filter for processing sequential measurements. The usual motion models (CV, CT, IMM)
    \item Can extend the filter by using EKF, UKF or particle filtering.
    \item Can extend further to state prediction by deep learning.
\end{itemize}

\subsubsection{Gating}
Points to make:
\begin{itemize}
    \item Important to reduce computational complexity
    \item Remove very unlikely associations before combinatory is involved.
    \item Can be simple distance heuristics or complex probability based methods.
\end{itemize}

\subsubsection{Data association}
\label{sec:anatomy-da}
Points to make:
\begin{itemize}
    \item What is decided: Hard (commit to one assignment), marginal/soft (weight measurements by association probabilities and keep one hypothesis), or deferred (keep several global hypotheses).
    \item How is the cost of association for the optimization algorithm decided?
    \item How is it solved: Approximately or exact (computational cost vs correctness)
    \item Some trackers do not use such solvers. Some have implicit data association (PHD) and end to end deep learning algorithms also handle association implicitly.
\end{itemize}

\subsubsection{Hypothesis representation}
\label{sec:anatomy-hyp}
Points to make:
\begin{itemize}
    \item Only relevant when several hypotheses are kept.
    \item When several hypotheses are kept, they can be stored in two ways. The distinction is mainly important for implementation.
    \item In a hypothesis-oriented representation each global hypothesis carries its own complete set of tracks.
    \item In a track-oriented representation each potential target keeps a tree of single-target hypotheses, and a global hypothesis is only a look-up of one leaf per target.
    \item Explain how track-oriented storage works and why it scales better. And how it improves pruning as well.
\end{itemize}

\subsubsection{Existence: birth, death and undetected targets}
\label{sec:anatomy-existence}
Points to make:
\begin{itemize}
    \item Binary existence, example; existence represented by a single hypothesis and existence probabilities (LMB) or multiple hypotheses and binary existence (GLMB)
    \item Birth to handle new targets arriving in the surveillance area; birth models
    \item Death (survival) used to terminate objects that leave the area or erroneous tracks.
    \item Low probability targets recycled back into the birth intensity (PMBM)
    \item Heuristics vs probabilistic approaches to the problems.
\end{itemize}

histories, and the number of these grows exponentially with time,
targets and measurements. Every practical tracker therefore applies a
chain of reductions (Fig.~\ref{fig:funnel}), and many design choices
that look like modelling decisions are really complexity decisions.

\subsection{Multiple sensors}
\label{sec:multisensor}

The pipeline in \autoref{fig:pipeline} describes a single sensor. Adding
sensors, for example a radar and an electro-optical camera, brings more
information, but it is not a block of its own. It changes how several
existing blocks are used and adds one new choice: where in the pipeline
the sensors are combined.

\paragraph{What changes for each sensor.} Every sensor $s$ comes with
its own sensor model: a measurement function $h_s$, noise covariance
$R_s$, detection probability $\PD^{s}$ and clutter model (Section~\ref{sec:anatomy}).
The tracker must apply the right model to each measurement, since sensors
differ in dimension, accuracy and false-alarm behaviour. Two practical
requirements follow. Measurements must be expressed in a common frame,
which requires the sensors to be registered to each other \TODO{cite}.
Sensors also rarely report at the same time, so the motion model must
support arbitrary time steps, and measurements that arrive late must be
handled \TODO{cite out-of-sequence measurement handling}.

\paragraph{Where the sensors are combined.} Three architectures cover
most of the literature (\autoref{tab:multisensor}). The choice is about
which association problem has to be solved, so it ties back to the
solvers in \autoref{tab:solvers}.

\paragraph{Relation to the families.} The architecture can in principle
be chosen independently of the family. Any recursive tracker can process
sensor scans sequentially, because each scan is just another set of
measurements with its own sensor model. In the exact Bayes recursion,
sequential and joint updates agree when the sensors are conditionally
independent given the targets. The family matters through cost and
through how much a truncation between sensors can lose, which is why
\autoref{fig:taxonomy} treats multi-sensor handling as orthogonal to the

\subsection{A map of the field}
\label{sec:map}

Two axes are enough to place almost every detection-based tracker
(Fig.~\ref{fig:taxonomy}). The vertical axis is the association
decision from Section~\ref{sec:anatomy-da}: how many association
hypotheses are carried between scans, and how they are stored. The
horizontal axis is the modelling framework: classical vector-based
models, or random finite sets (RFS). The second axis matters less than
it first appears. Methods in the same row share the same association
structure and complexity, and differ mainly in how carefully the
existence block is modelled. PMBM is therefore closer to track-oriented
MHT than to the PHD filter, and PMB and LMB are close relatives of
